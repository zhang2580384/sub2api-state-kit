### 4.6.0 质量探针

2026-09-25 在 Go `1.27.0` 执行 `go test ./...` 和 `go test -race ./...`：通过。面板测试 `app.test.cjs` 为 `29/29`，完整 UI 测试为 `36/36`。

质量探针是为了解决“新票可用但回答质量已经变化”的问题：

- 默认关闭，避免对所有用户产生额外模型消耗；
- 新票必须先通过原有同出口复验和网关/会话检查，再执行一次提示词验收；
- 只有回复包含任一配置答案时才发布新票；
- 未命中或探针失败时继续重打，当前仍有效的旧票保持服务；
- 质量请求返回的新状态和 Cookie 需要通过完整性检查后才保存；
- 探针不会成为永久白名单，也不承诺消除上游短时降智窗口。

本轮回归额外修复了两个边界：

- 关闭“打票指纹收敛”时，质量请求曾被通用探针逻辑强制为 `Reply with exactly: pong`，必然无法匹配自定义答案；
- 质量请求更新 Cookie/STATE 后，票据曾可能继续保存复验前的网关与会话绑定值。

### 4.5.2 路由 Cookie 完整性

- `780` 候选票必须同时存在非空 `__cflb` 和 `__oailb`；
- 缺少任一路由 Cookie 时，即使 `gateway_policy=any` 也拒绝候选票并快速重打；
- 规则层和引擎层分别覆盖缺少 `__cflb`、缺少 `__oailb` 两条路径；
- 业务出口复验、备用票恢复和持久化恢复使用同一完整性判断。

### 4.5.1 三态网关与诊断窗口

- 网关策略从单一白名单升级为 `allow / deny / any`；输入 `88,180,15` 会规范化为 `unified-15,unified-88,unified-180`；
- 默认策略为 `allow`，列表为 `unified-15,unified-88,unified-180`；`deny` 只拒绝列表内网关，`any` 不限制网关；
- `4.5.1` 的 `allow/deny` 会拒绝缺少 `__cflb`、`__oailb` 任一项或无法识别网关的候选票；`any` 的完整性缺口由 `4.5.2` 修复；
- 诊断面板按网关汇总出现、通过、模型不符、拒绝次数和通过率；
- 诊断事件常驻内存保留最近 5 小时，硬上限 5000 条，面板最多显示最新 2000 条；关闭面板不再清空，插件重启清空；
- 诊断窗口固定为大尺寸并可拖动，表格和网关统计区独立滚动，避免撑高宿主页面；
- 早前成功样本记录中的路由网关为 `unified-15`，而不是 `unified-88`；
- 同一网关号内仍可能同时出现正常和不正常输出，因此网关号不能单独证明不降智。

### 4.4.0 目标网关与 780 会话

- `780` 的签发时间从 Fernet 兼容负载读取，默认窗口为 `240` 秒；
- `4.4.0` 目标网关默认单一 `unified-88`，`4.5.1` 起改为三态网关策略；
- 打票返回的 `__cflb/__oailb` 必须完整、未过期并符合当前网关策略，否则候选票丢弃并快速重打；
- 同一账号只复用符合当前网关策略的上一轮路由 Cookie；
- 打票请求按参考实现收敛为 `codex-tui/0.154.0`、低推理、`tool_choice=auto` 和 `parallel_tool_calls=false`；
- `780` 业务请求注入绑定会话的 Cookie 与 `session_id`，同时兼容 `session-id`；
- 业务响应只在 STATE 仍匹配目标网关时滚动覆盖当前票据；
- 这些条件提高会话与网关一致性概率，不能仅凭票长、网关或模型声明证明不存在隐性降智。

### 4.3.2 780 滚动兼容

- `780` 默认关闭；打开后仍必须完成业务出口复验；
- 采集阶段拿到候选票后，保存业务出口复验响应返回的新票，而不是采集票；
- 复验返回 `312`、模型不一致或请求失败时丢弃候选；
- 业务请求响应中的新 STATE 和 `__cf_bm` 会滚动合并回当前票据；
- 成功样本的特征为 `cookie unified-15`、`780`、`Set-Cookie: __cf_bm`，以及票据在多次请求间滚动变化。

### 4.3.3 实时诊断监听修复

- 诊断面板打开时并行发送三次状态请求，避免串行等待超过插件端的监听检测窗口；
- 新增 UI 回归测试，验证三次状态信号并行发出；
- 诊断面板新增 `780` 类别显示回归测试；
- 三次状态请求全部失败时直接显示宿主错误。

### 4.3.1 配置页超时修复

- 官方 `v0.2.8` UI Bridge 仅支持 `config.load`、`config.save`、`config.test`、`plugin.status`、`ui.resize` 和 `ui.notify`；
- 旧版额外调用的 `proxies.list` 与 `accounts.list` 不存在，会固定等待 20 秒后返回“宿主响应超时”；
- `4.3.1` 已移除这两个调用，第一层代理直接保存为 `upstream_proxy_url`；
- 后端不再依赖列表返回的 `upstream_proxy_id`，保存时统一写入 `0`，代理链和票据逻辑保持不变。

### 4.3.0 保留的获取链路优化

- 生成出口的 IP 与地区合并为一次查询；
- 同出口复验只复核 IP 是否变化，不重复查询地区；
- 地区过滤、312、STATE 长度不符和复验失败使用快速重试；
- 旧模式可以提前准备备用票，优先复用当前生效的生成出口，复用失败后自动换新出口；
- 采集诊断耗时包含代理生成、出口检查和打票探测。

这些改动保留了“同出口复验通过后才可用”的安全边界，没有把未经复验的 STATE 直接投入业务。

## 真实代理探测

### 80 个独立出口质量对比

测试对象为单个固定账号、`gpt-6-astra`、固定提示词，每个种子先生成独立出口，再根据测试阶段发送后续请求。最终得到：

| 项目 | 结果 |
| --- | --- |
| 计划种子 | 80 |
| 可用种子 | 76 |
| 网络错误 | 4 |
| 样本事件 | 177 |
| 有效回答 | 173 |
| 无回答 | 4 |
| 回答 `15 / 16 / 17` | `71 / 68 / 34` |
| 全部样本事件 `17` 命中率 | `34 / 177 = 19.21%` |
| 有效回答 `17` 命中率 | `34 / 173 = 19.65%` |

按响应是否滚动返回新 `780` 分组：

| 分组 | 样本 | `17` | `17` 命中率 |
| --- | ---: | ---: | ---: |
| 返回新 `780` | 136 | 7 | `5.15%` |
| 未返回新 `780` | 41 | 27 | `65.85%` |

但“未返回新 780”不是稳定白名单：后续连续定向测试中，4 个种子、每个最多 12 次请求全部持续返回 `780`，只得到 `15/16`，没有再出现 `17`。另有样本在返回 `780` 时得到 `17`，所以该字段只能作为相关性线索，不能写成因果规则。

网关对比同样不支持固定白名单：

- `17` 出现在 `unified-160`、`165`、`193`、`198` 等多个网关；
- `rotation_request` 阶段的 64 个样本全部是 `15/16`，没有 `17`；
- 某些国家或 ASN 的小样本命中率较高，但受时间窗口、出口轮换和样本量影响，不具备生产级稳定性；
- 所有成功响应都带有相同的 `x-codex-safety-buffering-enabled: true` 和 `x-codex-safety-buffering-faster-model: gpt-5.6-luna`，不能作为区分依据；
- 固定 `unified-193` 的 20 次测试中 Cookie 指纹一致，质量仍发生变化，说明 Cookie 不是当次质量变化的唯一原因。

结论：不按网关、出口 IP、Cookie、`server_is_overloaded` 或固定 780 字节流做“不降智白名单”。插件采用发布前质量探针，把质量不合格的候选票挡在业务票之外；这是可验证的工程控制，不是对上游质量永久不变的承诺。

### 上游 292 生命周期

修正后的跟踪器记录到 6 个明确结束样本：

| 同一 292 持续 | 结束信号 |
| --- | --- |
| `6.05` 分钟 | `312 + gpt-5.6-luna` |
| `5.15` 分钟 | `312 + gpt-5.6-luna` |
| `5.00` 分钟 | `312 + gpt-5.6-luna` |
| `4.11` 分钟 | `312 + gpt-5.6-luna` |
| `1.13` 分钟 | `312 + gpt-5.6-luna` |
| `1.13` 分钟 | `312 + gpt-5.6-luna` |

这些样本的代理出口未变化，说明结束点是上游 292 会话变化，不是代理掉线或换 IP。`10` 分钟可能成功，但不能作为稳定下限。因此 Cookie 模式默认持续期设为 `300` 秒，备用票默认提前 `90` 秒。

### 粘性出口

使用：

```text
sessType=sticky&sessTime=180
```

`sessAuto=1` 的一次样本在约第 `18.74` 分钟更换出口，不能用于长期固定出口。改为 `sessAuto=0` 后，同一生成端口的出口已连续保持 `87.91` 分钟未变；尚未完整跑到 180 分钟。

### 旧模式：无 Cookie 跨出口

无完整 Cookie 时进行的跨出口对照试验为 `3/3` 次失败：

| 请求阶段 | 出口 | 结果 |
| --- | --- | --- |
| 采集 292 | 生成粘性出口 A | `292 + gpt-6-astra` |
| 使用同一 STATE | 第一层固定代理 | `312 + gpt-5.6-luna` |

切回原生成出口后恢复 `gpt-6-astra`。这说明旧模式不能只在打票阶段使用粘性出口，业务请求也必须保持同一出口。

### Cookie 分流：跨出口成功

保持完整 Cookie 和同一个 `session_id`，打票与业务使用不同出口的方案曾连续成功 `4/4`，业务响应继续返回目标模型。

结论：

- 打票响应必须提供 Cookie；只有 STATE 或只有 `session_id` 不算完整 Cookie 票据。
- 打票、复验和业务请求必须继续使用同一个 `session_id`，响应中更新的 Cookie 会合并回票据。
- 业务出口和采集出口不再强制相同，但香港 `HK` 和未知地区仍会被拒绝。
- 样本仍有限，不能把 `4/4` 当作所有账号、地区和上游状态下的永久保证。

## 精准快速出票

当前实现不是本地生成 292，无法保证每次快速、准确地得到 292。已实现的控制方式是：

- 提前准备备用票，而不是等当前票失效后同步获取；
- 当前票仍可用时继续服务，新票复验成功前不替换；
- 备用票晋级前检查账号身份、模型、业务出口、STATE、`session_id` 和 Cookie；
- 生成器模式可优先复用当前账号上一轮通过复验的出口；
- 可用“备用票提前量”平衡等待时间和代理调用频率。

尚不能保证：

- 生成器一次调用一定返回可用 292；
- 新票据一定在备用票提前量内完成；
- 单张 292 固定持续 5 分钟或更久；
- 所有出口、地区和账号具有相同成功率。

下一步若继续优化，应以真实诊断事件统计“生成器耗时、采集耗时、复验耗时、292 成功率、备用票命中率”，再根据 P50 / P95 调整提前量，而不是继续增加固定猜测值。
